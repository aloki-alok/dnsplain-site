How dnsplain works

dnsplain answers two questions about every domain you own: what is each record for, and is anything broken. This page explains how it reaches those answers, and why it's built to stay quiet unless it's sure.

Two views of the same domain

Your DNS provider holds the records you set. The internet holds what resolvers actually answer. Usually the two match. When they don't, something is wrong: the zone isn't the one in use, a target was deleted, or a sender's key moved.

So dnsplain reads both:

provider API ──► records you set ──┐
                                    ├──► compare ──► findings
live DNS ──────► what the internet ─┘
                 answers

Provider access comes from dnscontrol, which already speaks to 77 providers. dnsplain uses only its read calls: listing zones, reading records, and reading the zone's nameservers. One package in the code imports dnscontrol, so upgrading it touches one file.

Records become goals

A person thinks "this domain sends mail through Amazon SES". DNS stores a TXT record that says v=spf1 include:amazonses.com ~all. dnsplain keeps one table that maps record patterns to goals: the kind of job (mail, signing, website, ownership proof) and the service behind it.

The same table drives explain and the checks. That keeps them from disagreeing about what a record is. Adding a new service is a one-line change to the table.

Quiet unless sure

A tool that cries wolf gets ignored, and a false "critical" sends someone to change DNS that was fine. dnsplain follows three rules to avoid that:

  • A failed lookup is unchecked, never a problem. Timeouts and server failures say "couldn't check", not "broken".
  • Ask the way a receiver asks. DKIM is checked by requesting the key through your own name, exactly as a mail server would. An earlier version looked for an address on the key's host instead. It flagged 210 healthy Amazon SES keys, because SES leaves its inactive keys as empty text records with no address.
  • Every name is fully qualified. Lookups end with a dot, so your computer's search domains can't turn "server failed" into "doesn't exist".

Why read-only first

Changing DNS is the dangerous half of the job. A wrong write takes a website or a mail domain offline. dnsplain earns trust by being right about what it reads before it is allowed to write. A future version will change records through a fixed path: show the exact changes, wait for approval, save a snapshot, apply, then confirm the internet sees the change.
